# 종합 건강 분석 문구·화면 연동 협의안

작성일: 2026-09-22 · 상태: 프론트엔드·기획·건강 기준 담당자 검토용 초안

## 2026-09-22 화면 표시 확정 사항

1. **핵심 분석 지표 카드와 `분석 기준 및 출처 보기`의 주요 지표 판정 기준 목록**은 모두 메인 API의 `key_metric_keys[]`만 사용한다. 첨부 시안의 합성 사례에서는 체지방률·골격근량·공복혈당 3개다. 팝업 API의 `metrics[]` 전체를 반복 표시하지 않는다. 목록 순서는 `key_metric_keys[]` 순서를 따른다.
2. **`체성분 관련 추가 지표` 팝업**은 추천 근거의 `evidence_metric_keys[]`로 해당 지표의 값·판정을 조회한다. 제목 `체성분 관련 추가 지표`와 설명 `핵심 지표와 함께 참고한 보조 수치에요`는 사용자 조건이나 API 응답에 따라 바뀌지 않는 고정 UI 문구다. 백엔드 분석 문구로 생성하지 않는다.

`PopupResponse.metrics[]`는 판정 기준 목록과 추가 지표 팝업이 함께 참조하는 전체 데이터다. 백엔드에서 3개로 필터링하면 BMI·체중·체지방량 같은 보조 수치를 표시할 수 없으므로, 화면별 키 배열로 필터링한다.

## 먼저 합의할 화면

원격 `frontend` 브랜치의 `frontend/app/(health-data)/total-analysis.tsx`는 현재 문구와 판정이 고정된 화면이다. 이 화면에는 `headline`, `summary`, `goal`, `strategy`에 대응할 수 있는 영역이 있지만, 요청된 **핵심 지표 3개·추천 이유 아코디언·최종 추천 방향·세 팝업** 구성은 그대로 존재하지 않는다. `frontend/src/features/health-data/totalAnalysis.ts`의 목 데이터 타입도 현재 [메인 API 계약](main-analysis-api-contract.md)과 다르다. 이 화면을 새 시안으로 개편할지, 별도 화면을 사용할지 먼저 확정해야 한다.

## 데이터와 문구의 책임

| 항목 | 제안 책임 | 합의 기준 |
|---|---|---|
| 추천 판단 조건·문구 | 기획·건강 기준 담당자가 승인, 백엔드가 생성·저장 | 적용 지표, 기준 버전, 대상 조건, 예외 상태를 함께 정의 |
| 개인화 목표 | 백엔드 평가 시점 스냅샷 | 현재 프로필이 바뀌어도 과거 평가 문구가 바뀌지 않음 |
| 메인 문구·태그·근거 순서 | 백엔드 응답 그대로 표시 | 프론트에서 지표 순위·건강 판정·추천 이유를 재계산하지 않음 |
| 줄바꿈·말줄임·접근성 라벨 | 프론트엔드 | 백엔드 문구의 의미를 바꾸지 않고 작은 화면에서도 읽을 수 있게 표시 |
| 지표 표시명·아이콘 | 프론트엔드와 백엔드 합의 | 현재 팝업은 `key`와 `unit`은 주지만 표시명은 주지 않음. 키별 표시명 매핑을 프론트에 둘지 API에 필드를 추가할지 결정 |
| 일반 UI 상태 문구 | 프론트엔드·기획 합의 | 로딩·분석 없음·조회 실패·측정값 없음 등은 개인화 분석 결과와 구분 |

## 화면 필드 매핑 제안

| 화면 영역 | 메인 API | 팝업 API 또는 주의점 |
|---|---|---|
| 상단 제목 | `headline.title` | 고정 예시 문구를 대체 |
| 분석 요약 | `summary.title`, `summary.description` | 상태 배지는 별도 계약이 없으므로 문구에서 추측하지 않음 |
| 내 목표 | `goal.text` | 평가 당시 목표 문구 |
| 맞춤 제언 | `strategy.title`, `strategy.tags[]`, `strategy.message` | 태그 순서는 서버 순서 |
| 핵심 분석 지표 | `key_metric_keys[]` | 같은 `assessment_id`의 `metrics[]`와 키로 연결. 최대 3개 |
| 추천 이유 아코디언 | `recommendation_reasons[]` | 제목·설명·`evidence_metric_keys[]`를 서버 순서대로 표시 |
| 최종 추천 방향 | `final_direction.from`, `final_direction.to` | 두 문구를 그대로 표시 |
| 기준·출처 팝업 | 메인 응답의 `assessment_id`, `key_metric_keys[]` | 같은 평가의 팝업 API를 조회하고 주요 지표 판정 기준에는 핵심 키만 표시 |
| 체성분 관련 추가 지표 팝업 | `recommendation_reasons[i].evidence_metric_keys[]` | 같은 팝업 API의 `metrics[]`에서 근거 키를 찾고, 제목·설명은 위 고정 문구 사용 |

## 추천 문구 시안

아래 문구는 **임시 백엔드 생성 규칙으로 적용된 화면 검토안**이다. 평가 당시 목표와 각 지표의 확정 판정·기준·출처가 확인될 때만 반환한다. 추후 기획·건강 기준 담당자의 검토 결과에 따라 문구를 수정할 수 있다. 단일 검진 수치로 진단을 단정하지 않는다. 공복혈당의 선별 구간과 반복 검사에 관한 참고 자료는 [질병관리청 국가건강정보포털의 당뇨병 안내](https://health.kdca.go.kr/healthinfo/biz/health/gnrlzHealthInfo/gnrlzHealthInfoView.do?cntnts_sn=5305)다.

### A. 목표와 세 지표의 판정이 모두 확인된 경우

합성 조건: 사용자가 평가 당시 단기간 감량 목표를 입력했고, 같은 평가의 체지방률 `high`, 골격근량 `low`, 공복혈당 `caution` 판정과 기준 스냅샷이 있다.

| 화면 | 제안 문구 |
|---|---|
| 상단 제목 | 목표는 이어가되, 현재 상태를 함께 살펴봐요 |
| 분석 요약 제목 | 이번 분석에서는 체성분과 공복혈당을 함께 확인했어요 |
| 분석 요약 설명 | 체지방률은 높음, 골격근량은 낮음, 공복혈당은 주의로 평가됐어요. 각 판정에 적용된 기준도 확인할 수 있어요. |
| 내 목표 | 사용자가 평가 당시 입력한 목표를 그대로 표시 |
| 맞춤 제언 제목 | 체성분과 공복혈당을 함께 고려한 감량 방향 |
| 전략 태그 | 체성분 확인 · 근육량 확인 · 식사·활동 점검 |
| 전략 설명 | 목표 기간과 이번 측정 결과를 함께 보고 실행 계획을 정해요. |
| 추천 이유 1 | **체중 외 지표도 살펴봤어요** — 체지방률과 골격근량의 판정을 함께 확인했어요. `body_fat_percentage`, `skeletal_muscle_mass_kg` 연결 |
| 추천 이유 2 | **공복혈당도 함께 확인했어요** — 공복혈당에 주의 판정이 적용돼 식사·활동 계획을 검토할 때 참고해요. `fasting_glucose` 연결 |
| 최종 방향 | 단기간 체중 감량 → 측정 결과를 함께 고려한 감량 계획 |

이 조건에서는 `key_metric_keys`를 `body_fat_percentage`, `skeletal_muscle_mass_kg`, `fasting_glucose` 순서로 반환한다. 다른 조건에서는 확정 판정의 우선순위와 고정된 지표 순서로 최대 3개를 고른다. “빠른 감량은 근육 손실로 이어진다”, “지금은 반드시 근육을 지키며 감량해야 한다”처럼 개인의 인과관계나 처방을 단정하는 문구는 별도의 검증된 판단 근거가 정해질 때까지 사용하지 않는다.

### B. 적용 기준이 부족한 경우

지표 수치는 있지만 판정이 `unknown` 또는 `review_required`라면 해당 지표를 높음·낮음으로 표현하지 않는다. 저장된 메인 분석이 없고 임시 문구에 쓸 확정 판정도 없다면 **404 빈 화면**을 권장한다.

| 화면 | 제안 문구 |
|---|---|
| 제목 | 종합 분석을 준비하고 있어요 |
| 설명 | 입력한 건강 자료와 적용 기준을 확인한 뒤 분석 결과를 보여드릴게요. |
| 버튼 | 건강 자료 확인하기 |

이 상태에서 A 사례의 전략·추천 이유·예시 수치를 보여주지 않는다. 추후 부분 분석을 제공하기로 결정한다면, 백엔드가 별도 상태와 확인된 근거만 전달하는 계약을 먼저 정한다.

## 권장 화면 흐름

1. 상단 제목과 분석 요약으로 이번 평가의 핵심 메시지를 보여준다.
2. 평가 당시 목표와 맞춤 제언을 나란히 비교한다.
3. `key_metric_keys` 순서대로 최대 3개 핵심 지표를 카드와 주요 지표 판정 기준 목록에 똑같이 표시한다. 각 지표에서 실제 판정 기준 팝업으로 이동한다.
4. 추천 이유 아코디언에서 문구와 근거 지표를 함께 보여준다. `evidence_metric_keys`가 비어 있으면 추가 지표 버튼은 표시하지 않는다.
5. 최종 추천 방향과 출처 보기를 마지막에 둔다. 팝업은 메인 응답과 동일한 `assessment_id`로 조회한다.

## 상태별 표시 제안

| 응답·데이터 상태 | 화면 동작 |
|---|---|
| 메인 조회 중 | 개인화 문구·수치 대신 스켈레톤 표시 |
| 메인 404 | 평가 없음 또는 생성 가능한 분석 없음 안내. 예시 건강 조언·수치를 사용자 결과처럼 표시하지 않음 |
| 메인 401 | 로그인 갱신 또는 로그인 흐름으로 이동 |
| 메인 502·네트워크 오류 | 오류와 재시도 표시. 이전 사용자의 결과를 현재 화면에 남기지 않음 |
| 팝업 지표 `display_value=null` | 측정값 없음 표시 |
| 팝업 지표 `unknown`·`review_required` | `status_label`을 표시하고 확정 판정이나 범위표를 만들지 않음 |
| `ranges=[]` 또는 `sources=[]` | 기준·출처 정보가 없음을 안내. 예시 기준을 대체 표시하지 않음 |
| 출처 `url=null` | 원문 확인 버튼 비활성 |

## 합의가 필요한 결정

1. **화면 버전:** 현재 정적 `total-analysis.tsx`를 개편하는지, 사용자 요청의 새 종합 분석 시안을 별도 화면으로 구현하는지.
2. **문구 길이:** 각 제목·설명·태그의 허용 줄 수와 말줄임 정책. API의 최대 문자열 길이는 데이터 검증 한도이며 화면에 적합한 길이를 뜻하지 않는다.
3. **추천 규칙:** 어떤 확인된 목표·지표·판정 조합에서 어떤 문구를 허용하는지. 특히 빠른 감량, 근육 손실, 혈당 관리 같은 인과·건강 권고 문구는 승인된 판단 기준 없이는 생성하지 않는다.
4. **지표 범위:** 현재 팝업이 지원하지 않는 기초대사량·중성지방·허리둘레·HDL을 이번 화면에 포함할지. 포함한다면 저장·판정·출처와 팝업 API를 함께 확장한다.
5. **생성 방식:** 승인된 규칙을 백엔드에서 실행할지, 별도 분석 서비스의 구조화된 결과를 백엔드가 검증·저장할지.

## 검토 완료 조건

- 서로 다른 목표·건강 상태·판정 보류 상태를 포함한 최소 3개 합성 사례에 대해 메인 응답과 팝업 응답을 함께 검토한다.
- 모든 `key_metric_keys`와 `evidence_metric_keys`가 같은 평가의 `metrics[].key`에 연결된다.
- 건강 판단 문구마다 적용 지표, 실제 기준 스냅샷, 출처를 확인할 수 있다.
- 프론트는 로딩·404·부분 누락·오류 상태에서 예시 문구를 실제 분석 결과로 보여주지 않는다.

현재 백엔드는 저장된 결과의 조회·검증과 제한된 임시 문구 생성을 구현했다. 평가 생성 경로에 목표·기준 스냅샷 및 최종 분석을 저장하는 연결은 남아 있다. 프론트 화면 변경은 프론트 담당자가 진행한다.
