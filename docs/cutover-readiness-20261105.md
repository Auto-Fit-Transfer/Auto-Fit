# 백엔드 통합본 전환 준비 상태 (2026-11-05)

## 확인한 결과

- 통합 작업 중 기존 GitHub는 조회만 했다. 이 로컬 저장소에는 원격 저장소가 없다. 게시 대상은 공용 GitHub의 새 `back-end` 브랜치이며, 기존 `backend`와 `front-end`는 유지한다.
- 운영 Supabase 프로젝트 `eeeqibyssajykrhvecbv`의 적용 이력 80개는 이 저장소 마이그레이션의 앞 80개와 버전 순서가 같다. 운영에만 있는 버전은 없다. 운영 DB 조회는 모두 `SELECT`였다.
- 운영에 남은 마이그레이션은 아래 다섯 개다.
  1. `20261104060214_reconcile_live_diet_functions.sql`: 식단 추천·교체 RPC 정합화.
  2. `20261104060215_cache_exercise_ai_analysis.sql`: 운동 AI 분석 캐시 테이블.
  3. `20261104080053_enforce_ai_only_exercise_recommendations.sql`: 신규 AI 외 운동 추천 차단.
  4. `20261104081014_remove_legacy_exercise_paths.sql`: AI 운동 계약 강화와 이전 운동 시작 RPC 제거.
  5. `20261105020000_archive_non_ai_exercise_recommendations.sql`: 이전 규칙형 추천을 참고용 기록으로 전환하고 진행 중 세션을 중단.
- 로컬 Supabase(PostgreSQL 17)에서 85개 SQL을 처음부터 적용했고, 분석 캐시 테이블·AI 삽입 트리거·새 운동 시작 RPC·아카이브 제약조건을 확인했다. 이전 운동 시작 RPC는 제거된 상태다. 과거 추천·진행 중 세션·운동 로그·피드백을 만든 뒤 마지막 SQL을 재적용해 추천 `legacy/cancelled`, 세션 `stopped`, 로그·피드백 보존을 확인했다. 아카이브 기록에서는 항목 기록·완료·신규 피드백·분석·자세 분석·루틴 저장·커뮤니티 게시와 활동 선택이 거부된다. 신규 마일리지·챌린지·운동 순위와 과거 세션의 마일리지 순위 반영도 제외된다. CI에 전체 재현과 두 SQL 회귀 테스트를 추가했다.
- API·AI·OCR Docker 이미지 빌드가 모두 성공했다. 컨테이너의 API와 AI `/health`는 `ok`를 반환했다. OCR은 공급자 비밀값이 없는 상태에서 예상대로 `misconfigured`를 반환했다.
- 최신 테스트 결과: API 1,048개, AI 비실서비스 177개, OCR 4개 통과. Compose 정적 설정도 통과했다. API 테스트는 통합 코드·테스트·문서·배포 설정을 포함한 로컬 Docker 이미지에서 다시 실행했다. 배포 검사기는 API 문서와 테스트 경로가 모두 비활성화되었는지도 강제 확인한다.
- `demo/`의 로컬 웹 검증 화면은 정식 서비스 UI에 맞춘 홈·식단·운동·커뮤니티·마이 탭을 보여준다. 탭별 API 검증과 전체 검증 버튼으로 API 1,048개, AI 비실서비스 177개, OCR 4개, 도메인 격리 SQL 14종, DB 보관·업그레이드 SQL, Compose 정적 설정을 직접 다시 실행할 수 있다. 현재 작업 트리에서 테스트 이미지를 재빌드하며 로컬 7단계 검증을 실행한다. 앱 화면의 개인 기록은 예시이고 API 회귀 테스트는 가짜 의존성을 사용한다. 운영 서비스나 외부 AI는 호출하지 않는다. `demo/README.md`에 실행 명령이 있다.
- 로컬 Supabase Auth의 일회용 계정으로 API 인증·홈·프로필·식단·운동·커뮤니티·채팅·설정을 조회했고 13개 확인 단계가 모두 통과했다. 일회용 계정은 테스트가 끝난 즉시 삭제했다. 정식 프런트엔드 조회본 `ff3df41`을 로컬 API·로컬 Supabase에 연결해 로그인과 온보딩, 다섯 탭, 운동 설정, 채팅 응답도 브라우저에서 확인했다. 세부 결과는 `docs/local-web-staging-20261105.md`에 기록했다.

## 깨끗한 DB 재현에서 고친 부분

운영 `diet_meals.source_type`은 `NOT NULL DEFAULT 'db_catalog'`로 존재하지만, 앞선 SQL 파일들에는 컬럼 생성문이 없었다. 그래서 빈 DB에서는 `20261023030557_accept_rules_based_diet_meals.sql`의 제약조건 추가가 실패했다. 해당 파일 앞부분에 운영 스키마와 같은 `ADD COLUMN IF NOT EXISTS`를 추가했다. 또 과거 운동 SQL의 내부 규칙형 기본값·대체값을 중립적인 `legacy`로 바꿨다. 이 세 과거 파일은 운영에 이미 적용된 버전이므로 운영에서 재실행되지 않는다. 원래 로컬 파일의 SHA-256은 `supabase/migration-baseline-20261104.json`의 `original_local_sha256`에 남겼고, 같은 파일의 `sha256`은 새 DB 재현용 현재 파일을 검증한다.

## 운영 전환 전에 남은 조건

- 운영에는 이전 규칙형 운동 추천 75건(활성 59건·완료 16건), AI 추천 11건이 있으며, 이전 추천에 연결된 진행 중 운동 세션이 20건 있다. 다섯 번째 SQL은 이전 추천의 원본 항목·로그·기존 피드백을 남기면서 활성 추천을 `cancelled`, 진행 중 세션을 `stopped`로 바꾼다. 이 20건은 더 이상 이어서 기록·완료할 수 없다. 운영 적용 전 사용자 영향과 안내를 결정해야 한다.
- 기존에 지급된 마일리지 잔액과 티어 점수는 유지한다. 과거 운동 세션으로 새 마일리지·티어 점수·챌린지 진도를 만들지 않으며, 현재 운동·마일리지 순위에는 과거 세션과 직접 연결된 점수를 반영하지 않는다. 이미 지급된 챌린지 마일리지처럼 원천 세션을 식별할 수 없는 과거 보상은 잔액·마일리지 순위에 남을 수 있다. 이 보상을 소급 조정하려면 별도 운영 정책이 필요하다.
- 정식 `front-end` 브랜치 조회본 `ff3df41`의 운동 기록 화면은 세션이 `completed`이면 추천 생성 방식과 관계없이 `내 루틴으로 저장` 버튼을 표시한다. 새 API는 `session.recommendation_generator`와 `session.recommendation_status`를 반환하고 보관된 추천의 저장을 409로 거부한다. 로컬 조회본에 보관 상태 안내·저장 버튼 제한·웹 오류 안내 패치를 적용하고 실제 웹에서 확인했다. 정식 GitHub 브랜치에는 아직 반영되지 않았으므로 운영 전환 전에 프런트엔드 담당자가 패치를 검토·통합해야 한다. 정확한 계약과 패치는 `docs/frontend-archive-handoff-20261105.md`에 있다.
- 2026-11-05 읽기 전용 조회 당시 과거 운동 세션에 연결된 `posture_analysis_jobs`는 0건이었다. 적용 직전에 `processing`·`cleanup_pending` 또는 `temporary_video_path`가 있는 과거 세션 연결 작업을 다시 조회한다. 존재하면 임시 영상 삭제와 작업 종료를 먼저 완료해야 한다. 마지막 SQL의 조회 전용 트리거는 해당 작업의 후속 갱신도 막는다.
- 네 번째 SQL은 `start_exercise_session(uuid, uuid)`를 삭제한다. 기존 API 인스턴스가 이 RPC를 호출할 수 있으므로 DB만 먼저 변경하거나 이전 API만 되돌리는 전환은 안전하지 않다. 기존 트래픽 중지, 다섯 개 마이그레이션 적용, 새 API·AI·OCR로 전환을 하나의 점검 창에서 조율해야 한다.
- 실제 `deploy/stack/.env`, `api.env`, `ai.env`, `ocr.env`가 없다. 도메인/DNS/TLS, Supabase·OpenAI·Clova 비밀값, API↔AI/OCR 실연동은 아직 확인하지 못했다. `python3 deploy/stack/check_env.py`와 Compose 기동은 설정 후 수행한다.
- Chroma RAG 원문·임베딩은 저장소에 없다. RAG가 필요한 운영 환경에는 승인된 원문을 적재하고 검색 결과를 확인해야 한다.
- 일일 식단 갱신 GitHub Actions는 `DIET_REFRESH_SCHEDULE_ENABLED`가 `true`일 때만 실행된다. 공용 저장소 `back-end`의 URL·토큰을 검증하기 전에는 비활성 상태를 유지한다.
- 전환 전 운영 DB 백업의 복원 가능 시점과 이전 API/RPC 복구 절차를 확정해야 한다. 마지막 마이그레이션 뒤에는 이전 API만 재배포하는 것으로 롤백할 수 없다.

## 실제 전환 순서

1. 운영 백업과 복구 절차를 확인하고, 관리 가능한 점검 창을 잡는다. 이전 운동 세션 20건이 중단되는 사용자 영향과 안내를 확정한다. 과거 세션에 연결된 진행 중 자세 분석 작업·임시 영상이 없는지 다시 조회한다.
2. 네 가지 비밀 설정 파일을 안전한 배포 환경에 준비한다. `check_env.py`, DNS·TLS, RAG 적재, 스케줄 설정을 확인한다.
3. 이전 API 요청을 멈춘 뒤 운영의 미적용 다섯 마이그레이션을 순서대로 적용하고, 새 API·AI·OCR를 함께 기동한다.
4. 세 `/health`, 인증된 핵심 API, API→AI/OCR 호출, 새 AI 운동 추천·세션과 과거 기록의 조회 전용 상태를 확인한 후 트래픽을 연다.
5. 관측 결과가 기준을 벗어나면 트래픽을 다시 멈추고 준비된 DB·API 복구 절차를 실행한다. 이전 API 단독 복원은 사용하지 않는다.

운영 마이그레이션 적용·배포·기존 브랜치 정리는 아직 실행하지 않았다.
