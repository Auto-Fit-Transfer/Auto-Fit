## DB 트리거 적용 (2026-09-17)

`20260917013929_enforce_notification_settings_integrity.sql`을 실제 프로젝트에
적용했다. 물리 FK는 추가하지 않았다. 알림 설정의 모든 INSERT와 UPDATE는
활성 인증 사용자(`deleted_at is null`)와 프로필의 존재를 검사한다.
인증 행에는 FOR SHARE, 프로필 키에는 FOR KEY SHARE 잠금을 획득한다.
부모 삭제 및 키 변경 시 기존 사용자 ID의 알림 설정을 삭제하며, 인증 사용자의
소프트 삭제도 같은 방식으로 처리한다. 프로필 자체나 다른 사용자 데이터는
이 트리거가 삭제하지 않는다.

부모 TRUNCATE는 거부한다. 부모 삭제/키 변경/소프트 삭제는 READ COMMITTED
(또는 PostgreSQL에서 같은 의미인 READ UNCOMMITTED) 격리 수준에서 실행해야 한다.
고정 스냅샷이 잠금 대기 중 추가된 설정을 놓치는 것을 막기 위해 REPEATABLE READ와
SERIALIZABLE에서는 해당 부모 작업을 거부한다. 이 경로의 오류는 SQLSTATE 0A000,
없는 부모를 참조하는 설정 쓰기는 SQLSTATE 23503이다.

트리거 함수는 별도 `autofit_integrity` 스키마에 두고 고정된 빈 search_path를
사용한다. anon/authenticated/service_role의 직접 함수 실행 권한은 제거했다.
기존 RLS와 Data API 권한은 변경하지 않았다. DB 관리자에 의한 트리거 비활성화나
replication role 변경은 이 보호 범위 밖이다.

기존 인증 사용자 누락 9건은 유지했으며 유효한 사용자로 복구하기 전까지
설정 수정은 거부된다. 두 부모가 모두 없는 행은 여전히 0건이다.

검증: `backend/sql/notification_integrity_test.sql`을 실제 DB에서 실행하고
모든 테스트 변경을 롤백했다. 정상 생성·수정, 없는 부모 거부, 부모 키 변경,
삭제 및 소프트 삭제 연동, 함수 권한, 물리 FK 부재, 임시 테이블 TRUNCATE 차단,
REPEATABLE READ 부모 삭제 차단을 확인했다. 서로 다른 두 DB 세션에서 설정 생성과
프로필 삭제를 겹쳐 실행한 별도 테스트 후 잔여 설정은 0건이었으며 테스트 사용자는
삭제했다. 보안 Advisor에서 ERROR/WARN은 없고 기존 RLS 정책 없음 INFO 15건만 보고됐다.

참고: [PostgreSQL 행 잠금](https://www.postgresql.org/docs/current/explicit-locking.html),
[Supabase 함수 권한](https://supabase.com/docs/guides/database/functions).

삭제다. 업무 데이터가 없고 프로필이 빈 가입 기본값인 경우 인증 사용자만
삭제해도 기본 프로필과 알림 설정이 함께 정리된다. 삭제/소프트 삭제는

별도 MCP 연결의 pg_locks 조회에서 해당 표시와 PID 2530468을 확인한 다음
lock_timeout=1s로 부모 chats DELETE를 시도했다. 부모 행 잠금 대기로
SQLSTATE 55P03이 발생했다. 자식 트랜잭션은 정상 커밋했고, 이후 부모 DELETE는
protect_business_parent의 SQLSTATE 23503으로 거부됐다. 따라서 이 업무 관계에서
자식 우선/부모 우선 양쪽 실행 순서를 검증했다. 다른 모든 관계의 동시 실행을
개별 검증했다는 의미는 아니다.

테스트 메시지, 채팅, 인증 사용자를 자식부터 정리했다. 해당 사용자에 대한
profiles와 notification_settings를 포함해 테스트 행이 0건임을 확인했다.
물리 FK 및 새로운 운영 제약조건은 추가하지 않았다.

앞선 배포 환경 검증에서도 식단 API 30개, 채팅·운동 API 39개, 식단 브라우저
23개 검사가 통과했다. 브라우저는 로그인, 식재료 CRUD, 식단 생성·재생성,
섭취 처리, 날짜 이동, 화면 폭별 넘침 및 오류 로그를 확인했다.
이 검사는 관리자 API로 만든 합성 계정으로 수행했으므로 실제 사용자 화면의
회원가입·회원탈퇴 흐름 검증은 포함하지 않는다. 각 실행의 생성 계정은 정리했다.

### 의미상 참조 보호 적용 (2026-09-17)

`20260917021509_enforce_semantic_reference_integrity.sql`을 실제 DB에 적용했다.
물리 FK는 추가하지 않았다. notifications의 대상 없는 알림은 두 참조 값을 모두
NULL로 허용한다. 현재 코드·데이터에서 확인된 대상 유형은 report뿐이므로,
그 외 유형 또는 related_type/related_id 중 하나만 있는 입력은 23514로 거부한다.
새로운 대상 유형은 구현 시 검사와 부모 보호를 함께 확장해야 한다.
report는 실제 보고서 존재와 동일 사용자 소유를 FOR SHARE 잠금으로 검사한다.
참조 중인 보고서 삭제·소유자 변경은 23503으로 거부한다. 일반 내용 수정은 허용한다.
보고서 키 변경과 TRUNCATE는 기존 업무 부모 보호도 계속 적용된다.

exercise_logs 및 exercise_discomfort_logs에서 항목·세션이 모두 지정되면
두 부모를 FOR SHARE로 잠그고 같은 exercise_recommendation_id인지 검사한다.
불일치는 INSERT와 UPDATE 모두 23514로 거부한다. 항목 없는 세션 전체 불편 기록과
세션 없는 독립 운동 기록은 계속 허용하며, 지정된 개별 부모의 존재·소유자는
기존 업무 참조 트리거가 검사한다. 기록이 남은 항목·세션의 추천 변경은 기존
protect_business_parent가 차단하므로 부모 변경으로 검사를 우회할 수 없다.
새로운 세 함수의 직접 실행 권한은 PUBLIC/anon/authenticated/service_role에서 회수했다.

검증: 마이그레이션과 `backend/sql/semantic_reference_integrity_test.sql`을
동일 트랜잭션에서 실행한 뒤 롤백했고, 실제 적용 후 SQL 테스트도 다시 통과했다.
없는 보고서, 다른 사용자 보고서, 미지원 유형, 불완전 대상, 잘못된 알림 UPDATE,
참조 보고서 삭제·재할당, 동일 사용자 내 다른 추천의 운동 기록·불편 기록,
운동 로그 UPDATE 및 기록 후 부모 재할당을 차단했다. 정상 기록·알림 생성,
대상 없는 알림, 항목 없는 불편 기록 및 보고서 내용 수정도 확인했다.
적용 시 기존 알림·운동 로그·불편 기록 전체를 트리거로 재검사했다.
적용 후 해당 불일치 건수, public 물리 FK 및 세 함수의 클라이언트 실행 권한은 모두 0건이다.
관련 단위 테스트 43개와 git diff --check도 통과했다.

이번 적용 이후 다시 확인하지 못했다. 관리자 API 읽기 조회는 HTTP 200이었다.

### 계정 삭제 시 연관 자료 정리 (2026-09-17)

사용자 요청에 따라 `20260917021925_cascade_account_deletion.sql`을 실제 DB에
적용했다. 물리 FK는 추가하지 않았다. auth.users의 영구 DELETE 직전에
`aa_cascade_account_deletion`이 사용자별 업무 자료와 간접 자식 행을 자식부터
삭제하고 마지막으로 notification_settings와 profiles를 삭제한다.
기존 삭제 보호 트리거보다 먼저 실행되며, 정리 또는 검증이 실패하면 계정과
DB 자료 삭제 전체가 롤백된다. 계정 삭제 이외의 부모 삭제 보호는 유지된다.
auth.users의 soft delete는 이번 자동 정리 대상이 아니다.

공용 음식·운동 종류·약관·알레르기 종류·공용 메뉴 이미지 등 기준 자료는
삭제하지 않는다. 다른 사용자의 자료를 발견하면 23503으로 중단한다.
public의 user_id를 가진 기본 테이블은 실행 시 자동 발견하고, user_id 없는
자식은 business_references 35개 관계와 보고서 알림 참조를 따라 정리한다.
새 간접 관계는 반드시 관계 목록과 기존 참조 보호 트리거를 함께 추가해야 한다.

Storage 객체는 SQL로 메타데이터만 지우면 실제 파일이 남으므로 Storage API로
삭제한다. 직접 Auth 삭제 시 파일이 남아 있으면 DB 자료를 건드리기 전에
23503으로 거부한다. 파일까지 포함한 영구 탈퇴는 새 `DELETE /api/account`를
사용해야 한다. 삭제 대상은 get_current_user가 검증한 현재 사용자로만 정하며,
요청 본문이나 경로의 임의 사용자 ID를 사용하지 않는다.

탈퇴 API는 서비스 전용 begin_account_deletion RPC로 삭제 상태를 저장한다.
이는 auth 사용자 행 잠금을 통해 진행 중인 쓰기가 끝날 때까지 기다린다.
사용자 행과 소유자를 추적하는 간접 자식 및 Storage INSERT/UPDATE 트리거가
삭제 중 추가 저장·변경을 막는다. 서비스 키로 업로드한 owner_id=NULL 파일도
사용자 UUID 첫 경로 기준으로 차단한다. Storage UPDATE는 이전 소유자·경로도
검사하여 삭제 중 파일을 다른 경로로 옮겨 탈퇴 정리를 피하지 못하게 한다.

account_deletion_storage RPC는 owner_id 또는 첫 경로가 해당 사용자 UUID인
객체를 최대 500개씩 반환한다. API는 저장소별로 실제 객체를 삭제하고 다시
조회해 파일이 없어졌는지 확인한 후 Auth 관리자 삭제를 실행한다.
파일 소유자와 다른 사용자의 UUID 폴더가 충돌하면 자동 삭제를 중단한다.
파일·Auth 서비스 실패 시 HTTP 502를 반환하고 성공으로 표시하지 않는다.
일부 파일이 이미 삭제됐을 수 있으므로 이를 되돌리는 동작은 없으며,
계정과 DB 자료 및 삭제 중 상태를 유지해 같은 사용자로 다시 요청할 수 있다.
직접 DB 행 삭제나 관리자에 의한 트리거 비활성화는 정상 탈퇴 경로가 아니다.
외부 서비스 URL의 파일과 제공자 로그·백업은 이 사용자 자료 삭제 범위에 포함되지 않는다.

검증: 적용 전/후 `backend/sql/account_deletion_test.sql`이 통과했다.
채팅·식단·섭취·운동·건강평가·위험 예측·보고서·OCR의 직접/간접 테스트 자료를
정리하고 다른 사용자 자료와 공용 음식 데이터를 보존했다. 전체 public 테이블
행 수가 테스트 이전과 동일한 것도 확인했고 모든 테스트 변경은 롤백했다.
삭제 중 직접/간접 쓰기·설정 변경·Storage 경로 이동 차단, 재시도 및 권한도 검사했다.
기존 알림·사용자·업무·의미상 참조 SQL 테스트 네 종류도 적용 후 통과했다.
사용자 SQL 테스트의 영구 Auth 삭제 기대값은 삭제 거부에서 연쇄 정리로 변경했다.
프로필만 삭제하거나 soft delete를 실행할 때의 기존 보호 검증은 유지한다.

`backend/tests/account_deletion_live.py`에서는 로컬 백엔드 경로에 실제 Supabase
로그인 토큰을 전달해 20개 검사가 통과했다. 테스트 계정의 populated profile,
설정, 채팅·메시지, upload_files·OCR 및 health-documents/meal-photos의 실제 파일을
삭제하고, 삭제 후 기존 토큰의 API 거부와 잔여 DB 행·파일 부재를 확인했다.
이는 새 API의 로컬 코드와 실제 Supabase를 연결한 결과이며 Render 서버에
새 경로를 배포했다는 의미는 아니다. Render 자동 배포는 off이고 현재 세션에
Render 배포 도구·자격 증명이 없어 API 서버 배포는 남아 있다.

기존 합성 계정 생성의 HTTP 422 원인은 weak_password로 확인했다.
테스트용 무작위 비밀번호에 대문자·소문자·숫자·특수문자를 보장하는 접두부를
추가했다. 서버 비밀번호 정책은 변경하지 않았다. 변경 후 배포 채팅·운동 API
39개 검사가 통과했고 두 테스트 계정을 정리했다. 관련 단위 테스트 52개와
git diff --check도 통과했다. 삭제 테스트 계정 및 정리 대기 상태는 0건이며,
profiles/notification_settings/활성 Auth는 각각 10건이다.
Security Advisor ERROR/WARN은 없고 RLS 정책 없음 INFO 16건만 있다.
신규 private account_deletions는 클라이언트에 권한·정책을 주지 않는 내부 상태다.
