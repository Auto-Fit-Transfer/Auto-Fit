# 식단 생성 연동 확인 요청 — Frontend 담당자용

> 작성일: 2026-11-03
> 대상: Frontend 개발 담당자
> 관련 기능: 주간 식단 화면, 한 끼 재추천, 오류 표시

## 1. 결론

이번 식단 생성 실패의 직접 원인은 Frontend가 아니라 Backend에서 일반 채팅 API를 식단 생성에 사용한 경로입니다. 따라서 Frontend의 대규모 변경은 필요하지 않습니다.

Frontend는 AI Server를 직접 호출하지 않고 Backend API만 호출하며, 주간 생성과 한 끼 재추천을 서로 다른 동작으로 구분해야 합니다.

## 2. 담당 범위

| 사용자 동작 | Frontend 처리 |
|---|---|
| 최초 주간 식단 생성 | Backend의 주간 식단 생성 API 호출 |
| 저장된 주간 식단 조회 | Backend 저장 결과 조회 |
| 특정 한 끼 재추천 | 해당 요일·끼니 식별자를 Backend에 전달 |
| 전체 주간 식단 다시 생성 | 한 끼 재추천과 구분된 전체 갱신 동작 사용 |
| 레시피 상세 열기 | Backend를 통해 선택한 한 끼의 레시피 조회 |

AI Server의 `/recommend/diet*`와 서버 간 Bearer API Key는 Backend 전용입니다. Frontend에서 직접 사용하거나 노출하지 않습니다.

## 3. 필수 확인 사항

### 3.1 주간 식단 기준 화면 연결

정상 주간 식단은 월요일부터 일요일까지 7일이며, 각 요일에 다음 네 끼가 있습니다.

- `breakfast`
- `lunch`
- `dinner`
- `snack`

Frontend는 총 28개 슬롯을 표시할 수 있어야 합니다. 생성 중 일부 슬롯만 먼저 저장하거나 메뉴명만 임시로 채우는 동작은 Backend와 합의하지 않은 상태에서 추가하지 않습니다.

### 3.2 한 끼 재추천과 전체 재생성 구분

한 끼 재추천 요청에는 다음 식별 정보가 필요합니다.

- 선택한 요일
- 선택한 끼니 유형
- 현재 메뉴 식별 정보

응답 후에는 선택한 슬롯 하나만 교체하고 다른 요일과 끼니 화면 상태를 유지해야 합니다.

전체 주간 식단 다시 생성은 별도의 사용자 확인과 API 호출로 구분합니다.

### 3.3 영양정보 필드

메뉴 전체 화면에서는 다음 정보를 사용합니다.

- `estimated_calories_kcal`
- `nutrition.carbohydrate_g`
- `nutrition.protein_g`
- `nutrition.fat_g`

음식 item 또는 레시피 연결에는 다음 필드가 사용될 수 있습니다.

- `food_name`
- `portion_g`
- `calories_kcal`
- `carbohydrate_g`
- `protein_g`
- `fat_g`

`portion_g`는 내부 계산과 레시피 scaling에 사용되며, 화면에 반드시 노출할 필요는 없습니다. 레시피 화면에서는 완성 음식 중량보다 재료별 `name + amount_g` 표시를 우선합니다.

### 3.4 레시피 상세 화면

선택한 한 끼의 레시피 응답에서 다음 항목을 표시할 수 있도록 유지합니다.

- 메뉴명과 설명
- 메뉴 전체 열량 및 탄단지
- 태그와 맞춤 추천 이유
- 재료명과 `amount_g`
- 조리 단계와 단계별 시간
- 예상 총 조리 시간
- `recipe_source`
- 알레르기 또는 주의 문구

장보기 목록 추가 기능은 이번 AI Server 계약 범위에 포함하지 않습니다.

## 4. 오류 상태 표시

Backend가 제공하는 오류 코드를 기준으로 최소한 다음 상태를 구분하는 것을 권장합니다.

| 상황 | 사용자 표시 방향 |
|---|---|
| AI Server 일시 장애 | 잠시 후 다시 시도 안내 |
| 조건에 맞는 음식 후보 부족 | 조건을 조정하거나 다시 시도하도록 안내 |
| 알레르기 조건으로 추천 불가 | 안전 조건 때문에 생성하지 못했음을 안내 |
| 전체 생성 전 조회 | 아직 생성된 주간 식단이 없음을 안내 |
| 한 끼 재추천 실패 | 기존 메뉴를 유지하고 재시도 안내 |
| 레시피 준비 불가 | 식단은 유지하고 레시피만 unavailable로 표시 |

503 응답을 모두 “AI 서버가 준비되지 않음”으로 표시하지 않고 Backend 오류 코드와 메시지를 사용합니다.

## 5. 상태 보존 원칙

- 한 끼 재추천 실패 시 기존 메뉴를 삭제하지 않습니다.
- 레시피 조회 실패 시 주간 식단을 삭제하지 않습니다.
- 네트워크 재시도 중 동일 버튼의 중복 요청을 방지합니다.
- 재추천 성공 전까지 기존 슬롯을 화면에 유지합니다.
- Backend 저장 성공 응답을 받은 뒤 최종 화면 상태를 갱신합니다.

## 6. Frontend가 변경하지 않아야 하는 사항

- AI Server를 직접 호출하지 않습니다.
- AI Server API Key 또는 OpenAI Key를 앱에 포함하지 않습니다.
- Frontend에서 열량이나 탄단지를 임의로 다시 계산하지 않습니다.
- 누락된 음식 item을 임의 데이터로 채우지 않습니다.
- 한 끼 재추천 때문에 전체 주간 식단 상태를 초기화하지 않습니다.

## 7. 완료 조건

- [ ] 월요일부터 일요일까지 7일 28끼가 표시된다.
- [ ] 한 끼 재추천과 전체 재생성이 구분된다.
- [ ] 한 끼 재추천 성공 시 선택 슬롯만 변경된다.
- [ ] 재추천 실패 시 기존 메뉴가 보존된다.
- [ ] 메뉴 전체 열량과 탄단지가 올바른 필드에서 표시된다.
- [ ] Recipe의 재료별 `name + amount_g`가 표시 가능하다.
- [ ] 오류 유형별 안내가 구분된다.
- [ ] Frontend 번들에 서버 간 API Key가 포함되지 않는다.

## 8. E2E 확인 시나리오

1. 주간 식단이 없는 사용자가 최초 생성을 요청한다.
2. 생성 완료 후 7일 28끼를 조회한다.
3. 월요일 점심 한 끼를 재추천한다.
4. 다른 27끼가 유지되는지 확인한다.
5. 선택한 메뉴의 레시피 상세를 연다.
6. 메뉴 전체 영양정보와 재료별 중량을 확인한다.
7. 알레르기 조건으로 후보가 부족한 오류 화면을 확인한다.
8. AI Server 일시 장애 시 기존 저장 식단이 유지되는지 확인한다.
